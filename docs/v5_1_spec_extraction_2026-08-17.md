# v5.1 구현 명세서 추출 메모

## 핵심 목적

사용자 명세서는 0.5~5.0%의 실제 저점→고점 Swing이 최소 3회 이상 반복되는 종목을 찾아, 최대 300분 동안 구조 지속 가능성을 매분 재평가하는 수동 반복단타 스캐너를 요구한다. 목표는 5시간 뒤의 가격을 맞히는 것이 아니라 반복 구조의 지속성과 붕괴 가능성을 구분하는 것이다.

## 핵심 모듈

| 항목 | 명세 요구 |
|---|---|
| 지속성 | 90·180·300분 단계별 신뢰도, 장후반에는 남은 거래시간을 Horizon으로 사용 |
| Swing | 시간 순서가 있는 국소 저점→고점 Swing 3회 이상, 폭 중앙값과 주기 중앙값 산출 |
| 장세 | `TREND_SWING`, `RANGE_SWING`, `NONE` 분리 |
| 위험 | Soft Stop, Hard Stop, 동적 회복시간, `NORMAL_PULLBACK`·`SHAKEOUT`·`REAL_BREAKDOWN`·`HARD_EXIT` 상태머신 |
| 지속성 점수 | Swing 일관성, 폭 유효성, VWAP 체류, 60분 구조, 3중 유동성, 주기 안정성, 회복력, 스프레드 안정성, 피로도 감점 |
| 재진입 관리 | 종목별 쿨다운과 당일 Hard Kill |
| 후보 판정 | 모든 조건을 하나로 모은 `FINAL_BUY` |
| 확률 | 전략·점수 구간별 실측 표본 30건 이상일 때만 보정 확률 표시 |
| 속도 | 현재가와 구조 분석 주기 분리, 집중 분석과 자동 후보 모드 분리 |

## 명세의 한계로 명시된 내용

명세서 자체도 Persistence Score와 실제 5시간 지속 확률 또는 승률의 등치를 보장하지 않으며, 미국 세션 데이터 범위·사용자 체결가격·뉴스·거래정지·갭 급변은 별도 검증이 필요하다고 명시한다.

## 현재 앱과 비교할 핵심 쟁점

1. 현재 앱은 목표가·가짜신호·반복박스·기초 검증을 제공하지만 Swing 3회 기반 대표폭·대표주기는 미구현이다.
2. 현재 KIS REST 클라이언트의 미국 분봉 요청 범위는 120개이므로 300분 지속성 판단의 데이터 기반이 부족하다.
3. Streamlit Community Cloud는 장중 지속 수집·SQLite 영속 실행을 보장하는 환경이 아니므로 5시간 상태관리와 쿨다운은 외부 영속 저장소 또는 지속 실행 수집기 설계가 필요하다.
4. 현재 검증 저장소는 전략·세션별 결과 요약을 시작했지만 Calibration·윈도별 보정 확률·Hard Kill 상태를 아직 구현하지 않았다.

## 외부 운영 제약 근거

Streamlit 공식 문서는 Community Cloud의 로컬 파일 저장 지속성을 보장하지 않으므로 SQLite·JSON 파일만으로 신호 이력, 쿨다운, 당일 Hard Kill, 5시간 분봉 버퍼를 보관하면 재배포·재시작 시 손실될 수 있다고 명시한다. 이 상태는 Supabase 등 외부 데이터베이스로 옮겨야 한다.[1]

FINRA는 미국 프리·애프터 거래가 정규장보다 유동성이 낮고 변동성이 높으며, 불리한 가격·부분 체결·넓은 스프레드가 발생할 수 있다고 설명한다. 따라서 v5.1 명세의 3중 유동성은 미국 연장거래에서 별도 임계값으로 운용해야 하며, 정규장과 동일 점수의 신호를 동일한 위험도로 표시하면 안 된다.[2]
