# 반복단타 스캐너 v5.1 명세서 대비 현재 앱 검토 보고서

**검토일:** 2026-08-17 (KST)  
**검토 대상:** 사용자 제공 `반복단타 스캐너 v5.1 최종구현명세서`, 현재 GitHub `ymym`의 Streamlit 앱 및 `scanner` 모듈  
**검토 목적:** 명세서에서 유지할 항목, 삭제·교체할 항목, 새로 구현해야 할 항목을 정하고 현재 앱을 실제 반복단타 목적에 맞는 구조로 발전시키는 것이다.

> 이 보고서는 구현과 검증을 위한 설계 문서이며, 특정 종목의 매수·매도나 수익·승률을 보장하지 않는다. 특히 “80% 승률”은 신호 점수가 아니라 시장·세션·전략별 비용 반영 실측 결과로만 검증할 수 있다.

## 1. 결론

v5.1 명세서의 방향은 현재 앱보다 사용 목적에 더 가깝다. 핵심은 단순히 ‘0.5~5.0% 박스가 있는지’를 찾는 것이 아니라, **실제 저점→고점 Swing이 여러 번 반복됐는지, 그 주기와 폭이 유지되는지, 정상 눌림인지 실제 붕괴인지, 재진입이 가능한지**를 상태로 관리하는 데 있다. 이 방향은 유지해야 한다.

다만 명세서에 ‘구현 완료’라고 적힌 여러 기능은 현재 `ymym` 코드에는 존재하지 않는다. 현재 앱은 진입·1차·2차 목표·구조 무효화·기초 가짜신호 필터·거래량·거래대금·스프레드·전략별 검증 요약까지 구현했지만, **Swing 3회 기반 통계, Persistence Score, Pattern Fatigue, Soft/Hard Stop 상태머신, 종목별 Cooldown/Hard Kill, 보정확률, 지속 수집 데이터 계층**은 아직 없다.

따라서 “v5.1의 모든 숫자와 조건을 즉시 화면에 추가”하는 방식은 권고하지 않는다. 먼저 거래일 전체의 분봉·상태를 잃지 않는 데이터 구조를 만들고, 그 위에 순수 함수 형태의 Persistence Engine을 넣은 뒤, 실제 신호 결과로 임계값을 검증해야 한다.

## 3. 반드시 유지할 현재 앱 기능

현재의 **가격 계획 화면**은 유지하는 것이 맞다. 사용자는 현재가, 진입 기준가, T1, T2, 구조 무효화 가격을 한 화면에서 읽고 싶어 하며, 이 기능은 v5.1의 Soft/Hard Stop과 Swing 기반 목표가를 표시할 가장 적절한 UI 기반이다.

현재의 완료봉 원칙, 실제 매수 참고가(매도 1호가) 사용, 비용 반영 손익비, 가짜 돌파·윗꼬리·하향 이탈 경고, 세션별 스프레드 게이트도 유지해야 한다. 특히 미국 연장거래는 정규장보다 유동성이 낮고 변동성이 크며 불리한 체결가와 넓은 스프레드가 나타날 수 있으므로, 프리·애프터의 신호를 정규장과 같은 기준으로 평가하면 안 된다.[1]

현재 검증 저장소의 전략·세션별 분리는 v5.1 Calibration의 출발점으로 활용할 수 있다. 다만 현재 30분 평가만으로 ‘5시간 지속성’을 검증할 수는 없으므로, 검증 기간과 결과 정의를 확장해야 한다.

## 5. 새로 추가할 핵심 엔진

### 5.1 `persistence_engine.py`

새 엔진은 Streamlit UI와 분리된 순수 Python 모듈이어야 한다. 같은 분봉 입력에는 같은 결과가 나와야 하며, 화면·DB·KIS 호출이 전략 계산을 섞지 않아야 테스트와 검증이 가능하다.

| 구성 요소 | 입력 | 출력 |
|---|---|---|
| Swing 추출기 | 완료 1분봉 | 시간 순서 L→H·H→L Swing 목록, 폭·상승/하락시간 |
| Swing 통계 | Swing 목록 | 대표 폭 중앙값, 대표 주기 중앙값, 일관성, 최근 3회 축소 여부 |
| Persistence Scorer | Swing·VWAP·60분 구조·유동성·스프레드·피로도 | 점수, 등급, 90/180/300 신뢰 상태, 감점 근거 |
| Risk State Machine | Soft/Hard Stop·회복 시간·현재 분봉·수급 | `NORMAL_PULLBACK`, `SHAKEOUT`, `WARNING`, `REAL_BREAKDOWN`, `HARD_EXIT` |
| Cycle Manager | 종목·거래일·위험 이벤트 | 쿨다운 종료시각, Hard Kill 여부, 재진입 허용 여부 |
| Final Decision | 위 모든 결과 | `FINAL_BUY`, `WAIT`, `BLOCK` 및 명확한 게이트 목록 |

### 5.2 상태 저장과 검증 스키마

외부 DB에는 `minute_bars`, `signal_events`, `cycle_state`, `calibration_summary`를 분리해 보관해야 한다. `minute_bars`는 심볼·시장·세션·거래일·시간을 복합 키로 두고 중복을 제거한다. `cycle_state`는 `REAL_BREAKDOWN`, `HARD_EXIT`, 쿨다운 만료시각, Hard Kill 횟수를 거래일별로 저장한다. `calibration_summary`는 전략·세션·점수 구간별 T1-before-stop 결과, 순수익률, 표본 수를 저장하며 30건 미만은 확률 공란으로 표시한다.

### 5.3 데이터 준비도와 장마감 처리

| 데이터 상태 | 화면 상태 | 신규 진입 |
|---|---|---|
| 0~29분 | `EARLY_FORMING` | 금지 |
| 30~89분 | `EARLY_PROJECTED` | 관찰 중심; 강한 모든 게이트 통과 시에만 참고 |
| 90~179분 | `PROJECTED_90` | 반복구조 후보 평가 가능 |
| 180~299분 | `PROJECTED_180` | 지속성 추정 신뢰 강화 |
| 300분 이상 | `OBSERVED_300` | 실제 5시간 구조 기준 평가 |
| 남은 장 45분 미만 | `EXIT_MANAGEMENT` | 신규 진입 금지 |

## 6. 실시간 운영 방식 비교

명세의 ‘5시간 지속성’은 앱을 열었을 때만 실행되는 화면만으로는 충족하기 어렵다. 아래 두 방식은 모두 가능하지만 충족 범위가 다르다.

| 방식 | 장점 | 한계 | 비용·설정 복잡도 |
|---|---|---|---|
| 현재 Streamlit 앱 중심의 수동 집중 분석 | 즉시 사용 가능, KIS 호출량 관리가 단순, UI 개선을 바로 사용 가능 | 앱 재시작·미접속 시간의 분봉과 Cycle 상태가 누적되지 않아 실제 5시간 검증 불가 | 낮음; 현재 환경 유지 |
| 지속 수집기 + 외부 DB + Streamlit 표시 화면 | 1분봉·Cycle·Calibration을 장중 지속 보관, 90/180/300 상태와 Hard Kill을 실제로 관리 가능 | 별도 데이터 수집 프로세스, 외부 DB, KIS 호출·세션·장애 관리가 필요 | 중간 이상; 지속 실행 환경과 DB 설정 필요 |

두 번째 방식만이 v5.1의 5시간 지속성·쿨다운·보정확률 요구를 충족한다. 첫 번째 방식은 사용자 선택 종목의 설명형 스캐너로 유지하고, 두 번째 방식의 수집·상태 엔진을 별도 계층으로 추가하는 것이 가장 안전한 통합 방법이다.

## 8. 현재 즉시 적용하지 말아야 할 항목

보정확률을 현재 점수에서 직접 계산해 표시하는 기능은 아직 추가하면 안 된다. 현재 검증 표본은 부족하고 30분 평가도 v5.1의 대표 Swing·T1-before-stop 정의와 일치하지 않기 때문이다. 또한 v5.1 문서의 특정 임계값(예: 70점, ATR 0.80, 10·15분 쿨다운)은 출발 가설로는 사용할 수 있지만, 한국 정규장·미국 프리·정규·애프터 전체에 동일하게 확정하면 과적합 또는 비현실적 체결 가정이 될 수 있다.

## 9. 적용 권고

현재 앱에서 바로 활용할 기능은 **설명형 가격 카드·차트·세션별 스프레드·기초 가짜신호·전략별 검증 저장**이다. 이를 지우지 않고, 신규 `persistence_engine.py`를 중심으로 Swing 구조·지속성·위험 상태·Cycle 상태를 추가해야 한다.

다음 개발은 한 번에 모든 UI를 바꾸는 대신, 먼저 외부 DB 스키마와 순수 전략 엔진을 만들고 테스트 데이터로 Swing·Stop·Cooldown을 검증한 뒤 화면에 읽기 전용 진단을 붙이는 순서가 적절하다. 이후 실제 장중 실측 데이터를 축적해 Calibration을 켠다.
