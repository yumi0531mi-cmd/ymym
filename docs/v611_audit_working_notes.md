# v6.11 실패 표본 감사 작업 노트

## 화면에서 확인한 고정 사실

- 감사 버전은 `6.11-isolated-boundary-capture`이며, 완료 표본은 27건이다. 세 시간대 방향을 모두 맞힌 표본은 4건이고 하나 이상 방향에 실패한 표본은 23건이다.
- 사용자가 지정한 20건 성능 스냅샷은 5분 25.0%, 15분 20.0%, 30분 25.0%였다. 감사 화면의 27건은 같은 버전에 후속 완료된 표본이 더해진 원문 집합이다. 분석에서 20건 성능 수치와 27건 감사 원문을 혼용하지 않는다.
- v6.11은 신호 시점의 `Direction Engine` 상세와 시간축별 입력 지표를 저장하지 않아 감사 표의 해당 필드는 5·15·30분 모두 `미기록 27`로 나타난다. 따라서 v6.11 저장 원문만으로는 당시 지표의 실제 수치·원점수·후속 방향 변환을 재구성할 수 없다.
- 실패 원문 상단에는 `US_PRE` 세션의 SKHY·SPCX·INTC·TQQQ·AAOI가 반복되어 있으며, `WATCH · NONE · 장세 전환 대기`, `WATCH · NONE · 하락 구조`, `WATCH · RANGE_SWING · 박스 하단 평균회귀`, `REVERSAL_MEAN_REVERSION · RANGE_SWING`이 보인다.

## 감사 원칙

- v6.11의 실측 성능 실패는 수정 필요성을 뒷받침하지만, 저장하지 않은 신호 시점 입력을 사후 추정해 원인으로 단정하지 않는다.
- 이후 수정은 v6.11의 반복된 구조·시간축 준비 문제와 현재 코드의 재현 가능한 계산 흐름을 대조해 코드상 확정할 수 있는 오류·중복·시간축 불일치에만 한정한다.
- 수정 버전은 현재 v6.11과 입력 상세를 분리 저장하고, 국내장 신규 표본 20건 이상으로 독립 검증한다.

## 국내장 이력 확보 확인 대기

v6.18 국내 수집 화면은 완료 1분봉 119개와 경로 준비 `False`를 표시했다. 이는 15분 30개와 30분 20개 완료봉 요건을 충족할 수 없는 이력 길이였으며, 성능 표본을 만들지 않는 것이 정상 동작이다. KIS 공식 국내 일별분봉 샘플은 한 호출 최대 120건이지만 `FID_INPUT_DATE_1`과 `FID_INPUT_HOUR_1`로 과거 날짜·시간 분봉을 조회할 수 있다고 명시한다. 따라서 v6.19는 이 공식 파라미터를 사용해 가장 이른 행 직전 시각부터 최대 6페이지를 연속 조회한다.

v6.19 공개 국내 수집 화면은 재배포 직후 후보 자동 분석을 시작했고, 호출 보호는 1분 6/30·5시간 6/1100으로 표시됐다. 아직 후보 분석 진행 중이므로 완료 1분봉 수·경로 준비 상태·신규 표본 시작 여부는 분석 완료 후 다시 확인해야 한다.

v6.20은 장 시작 전 커서가 반복되는 경우를 방지하기 위해 직전 날짜 15:30으로 넘기고, 동일 시각 페이지가 다시 오면 즉시 중단하도록 배포했다. 재배포 직후 공개 국내 화면은 다시 후보 분석 진행 상태였고 호출 보호는 1분 7/30·5시간 7/1100이었다. 아직 최종 카드와 표본 시작 결과가 렌더링되지 않아, 실제 KIS가 이전 거래일 행을 반환했는지는 화면 분석이 끝난 뒤에만 판정한다.

30초 추가 대기 뒤에도 화면은 동일한 후보 분석 진행 상태와 1분 7/30·5시간 7/1100 표시를 유지했다. 이 상태만으로는 요청이 정상적으로 이전 거래일 이력을 조회 중인지, 특정 KIS 호출이 대기·재시도 중인지는 구분할 수 없다. 따라서 완료 화면이나 명시적 오류가 나오기 전에는 실제 720개 이력 확보 성공으로 기록하지 않는다.

최대 응답 대기 후 v6.20 화면은 후보 분석을 완료했고, `005930` 1건의 고정 예측 표본을 실제로 시작했다. 화면은 5분 상승·15분 상승·30분 박스 방향을 표시하고 5·15·30분 실제가 경계를 각각 대기 상태로 표시했다. 이는 적어도 한 후보에서 15·30분 경로 준비가 성공했음을 뜻한다. 완료 표본 수는 아직 0이므로 방향 적중률이나 수정 효과는 판정하지 않는다.

v6.20의 15분·30분 경계 대기 중 Supabase 영속 조회 예외가 화면을 중단시킨 사실을 확인했다. v6.21은 이전 재배포 세대의 `PersistenceError`도 비치명적 저장소 오류로 분류하고, EventStore·CycleStore 캐시 계약을 새로 분리해 재생성한다. 배포 직후 국내 화면은 오류 화면 없이 후보 분석을 재개했지만, 표본 경계 완료 전에는 수집 안정성 통과로 판정하지 않는다.

v6.21 공개 국내 화면은 오류 화면 없이 3개 동시 표본을 표시했고, 가장 이른 `005930`의 5분 실제가는 다시 `수집 완료`였다. 15분·30분은 각각 대기 상태이며 완료 30분 표본은 0건이다. 따라서 저장소 오류가 첫 5분 경계를 통과한 것은 확인됐지만, 모든 시간대 수집 안정성 판정은 30분 경계 완료 후에만 한다.

이후 수집 안정성 우선 모드는 대기 표본 5/5에 도달해 카드 재분석을 멈추고 5·15·30분 실제가 경계 저장을 우선했다. 가장 이른 표본의 5분 실제가는 계속 수집 완료였고, 나머지 네 표본은 신호 시각 순서대로 5분 대기 상태였다. 이 화면에는 DATA_MISSING이 표시되지 않았으며, 15분과 30분 완료 전이므로 성능 평가는 보류한다.

다음 확인 시에는 5개 표본 모두 5분 실제가가 수집 완료였고, 가장 이른 `005930`의 15분 실제가도 수집 완료였다. 나머지 15분과 다섯 표본의 30분 경계는 대기 상태였다. 영속 조회 오류 화면은 재발하지 않았고 DATA_MISSING 표시도 없었다.
